# Sincronización de identidades del dispositivo — implementación local

`POST /api/v2/devices/station/identities/synchronize` se registra únicamente si `CHECADOR_IDENTITY_SYNC_ENABLED=1`. Requiere TLS y Device Auth (`X-Device-Id`, `X-Credential-Key`, `Authorization: Bearer ...`). Cuerpo JSON exclusivo: `{"request_id":"11111111-1111-4111-8111-111111111111"}`; UUID en formato hexadecimal minúsculo. No se aceptan IDs de dispositivo, estación o trabajador desde el cuerpo.

La API revalida credencial y grant biométrico ligado a esa credencial bajo bloqueo, así como estación física activa y mapeo canónico único. Selecciona personal activo por estación sin consultar huellas. Conserva identidad actual inequívoca, crea UUID v4 para personas sin historial V2 en ningún dispositivo, e informa como conflicto los demás casos. No modifica identidades históricas. Cada inserción es verificada por readback y toda la solicitud, incluidos resultados parciales e idempotencia, confirma en una única transacción.

200: `{"request_id":"...","created":2,"preserved":1,"conflicts":1}`. La pareja dispositivo/request_id conserva el resultado confirmado; al repetir, devuelve exactamente ese resultado. La misma clave tras un cambio de estación devuelve 409 `IDEMPOTENCY_CONFLICT`. Entrada inválida: 400 `BAD_REQUEST`; credencial inválida/revocada: 401 `DEVICE_UNAUTHORIZED`; grant o estación inválida: 403 `DEVICE_SCOPE_DENIED`; método: 405; contenido: 415; error transaccional o dependencia: 503 `SYNC_UNAVAILABLE`. Ninguna respuesta incluye huellas, secretos o datos de otra estación.

La tabla de idempotencia se describe en `CHECADOR_V2_DEVICE_IDENTITY_SYNC_DDL_PROPOSAL.sql`. Es propuesta para revisión de tipos, índices y permisos; no aplicada a preproducción. La ruta permanece desactivada por defecto. La compatibilidad real del Lector, la autenticación bajo concurrencia y el roster posterior requieren ejecutar la suite MariaDB y las pruebas de integración reales; no son PASS por inspección.
